# The Aldermarch (working title)

Async 2-4 player county-conquest strategy for mobile. Inspired by Lords of the
Realm II, deliberately divergent from it in several places.

**The title is a placeholder.** "Aldermarch" is the map name being reused as a
project name; it is not cleared for trademark. Run any finalist through USPTO
TESS and App Store / Google Play search before committing to it.

```bash
npm install
cp .env.example .env   # then paste your PixelLab token in
npm run dev            # dev server
npm test               # domain + map + manifest tests
npm run typecheck
npm run build
npm run gen:map        # regenerate map geometry from its layout spec
npm run art:balance    # PixelLab credits / generations remaining
npm run art tools/art-batches/<batch>.json   # generate an art batch
```

### PixelLab token

`.mcp.json` reads the token from `${PIXELLAB_API_KEY}` so it is never
committed. **If that variable is unset, every PixelLab call fails with
`401: Invalid API token`** — the header ships with the placeholder unexpanded.
That failure looks exactly like a bad token, so check the variable first.

Set it in `.env` (gitignored). `tools/pixellab.mjs` reads `.env` directly, so
art generation works even when the editor's MCP session started without the
variable. Note that MCP servers initialise at session start: after setting the
variable you must restart the session for the MCP tools themselves to pick it
up.

## Where things live

```
src/
  domain/          Pure game rules. No React, no rendering, no I/O.
    ids.ts         Branded id types
    resources.ts   Food (per-county) vs materials (pooled) split
    map/           Static map types + queries (adjacency, movement, chokepoints)
    match/         Match state and creation
  content/         Data, not code — factions, units, maps
  assets/          Asset manifest + resolver
  ui/              React rendering
tools/             Dev scripts (map geometry generator)
```

## Four decisions worth knowing before editing

### 1. There is no single-player data structure

Every match — solo included — is a `MatchState` with a `players` array where
each player is human or AI. `createSoloMatch` is a thin wrapper over the same
`createMatch` a networked game uses. Milestone 1 is single-player on this
architecture; Milestone 2 wires the identical state to Firebase.

`MatchState` is JSON-serializable throughout: no class instances, no `Map`/`Set`,
no `Date`, timestamps as epoch ms. Anything that does not survive
`JSON.parse(JSON.stringify(x))` does not belong in it. Collections addressed by
id are keyed records rather than arrays, because Firestore merges keyed maps
field-by-field but replaces arrays wholesale.

Derived values are never stored — army strength, income and territory counts are
computed, so two clients cannot disagree about them.

### 2. Game logic never names an image file

Art resolves through `src/assets/manifest.json` via typed accessors
(`terrainArt`, `unitArt`, `castleArt`, …). A test walks the whole `src` tree and
fails on any image path outside the manifest module.

Manifest entries carry `pending: true` until PixelLab has generated the file.
Pending entries deliberately resolve to `url: null`, so callers draw their
fallback instead of pointing an `<image>` at a 404 — which is exactly the bug
that filled the first map render with broken-image glyphs.

### 3. All shipping art comes from PixelLab

Sprites, tiles, unit icons, buttons, banners, borders, panel chrome — all of it
is generated through the PixelLab MCP tools and referenced through the manifest.
This repo does not hand-author final art: no hand-drawn SVG, no CSS gradients or
shapes standing in as the finished visual.

The current build leans on the one allowance — flat palette colour as a
**clearly interim, tracked** stopgap. Every such stopgap is registered in
`src/ui/interimArt.ts` against the manifest key that retires it, and a test
fails if a stopgap outlives the art that was meant to replace it.

The pipeline order is fixed: **map design is decided here first**, then the art
request is written from that design, then PixelLab generates, then the design is
rendered with the result. PixelLab is never asked to make a design or balance
call.

### 4. The map's design claims are tested

`src/content/maps/aldermarch.test.ts` asserts the properties the map is supposed
to have, because balance rots silently otherwise — a chokepoint stops being a
chokepoint the moment someone adds one border.

Geometry is generated by `tools/generate-map-geometry.mjs` from a rows/columns
spec, seeded so it is reproducible. Hand-authoring polygons that tile without
hairline slivers is error-prone; the generator guarantees shared borders use
identical vertices, and a test checks it.

## The Aldermarch map

19 counties in two nine-county basins joined by a single county.

- **One deliberate chokepoint.** Ironthroat is the only link between the basins,
  verified by an articulation-point test. It is size 1 — a gate, not a place to
  grow — and it carries stone, so holding it is an economic decision as well as
  a positional one.
- **Scarce stone.** 3 of 19 counties produce it, and castle tiers need it. One
  sits in each basin (both adjacent to the pass) and one is the pass itself. No
  starting county produces stone, so every player must expand or trade for it.
- **Structurally identical seats.** The layout mirrors about the pass and about
  the vertical centreline. All four seats have the same neighbour count, the
  same terrain mix within early reach, and the same road distance to the pass.
  Variety lives in county sizes and resources, not in seat advantage — a seat
  that reaches the chokepoint a hop sooner is simply the better seat, and no
  amount of resource tuning fixes that.
- **A road spine** runs the length of the map through the pass, so the fastest
  route between basins is also the contested one.

The layout is original. It follows the source game's design patterns without
reproducing any published map's arrangement.

## Open design questions

Carried from the design doc, deliberately modelled as config rather than
hardcoded so playtesting can settle them:

- Turn-timeout fallback — `MatchConfig.timeoutPolicy`, currently defaulting to
  `autoSkip`.
- Final victory-condition menu — `MatchConfig.victoryConditions`.
- Map size ↔ player count pairing.

## Accuracy note

Where this codebase encodes specifics attributed to Lords of the Realm II
(costs, pacing numbers, formulas), those are first-pass values, not verified
citations. The design doc's account of already-fact-checked mechanics — the
shared-treasury model, mercenary bands, movement points — is treated as
authoritative over recollection.
